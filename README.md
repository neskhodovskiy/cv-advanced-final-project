# Як деградація відео впливає на зіставлення зображень

Курсовий проєкт Computer Vision Advanced. Досліджуємо, чи допомагає локальне вирівнювання контрасту (CLAHE) розрізняти відповідні та невідповідні пари зображень після стиснення або розмиття. Контекст задачі — камера без попереднього калібрування, відсутність GPS під час спостереження та обробка запису на наземній станції. В експерименті алгоритм отримує **одну заздалегідь сформовану пару** і повертає оцінку її відповідності. Маршрут у демо походить з анотацій.

## Швидкий запуск

Потрібні Docker із Compose та інтернет для першої збірки. Виконайте з каталогу клонованого репозиторію:

```sh
docker compose up --build
```

Відкрийте [демо на localhost:8080](http://localhost:8080). Під час першого запуску сервіс готує коротку авторську синтетичну сцену. Вона входить у проєкт у вигляді генератора, працює на CPU і доступна без завантаження дослідницьких наборів. Зупинка — `docker compose down`.

Призупиніть запис, перемкніть чистий кадр на H.264 або розмиття та ввімкніть CLAHE. На тій самій позиції можна порівняти пари точок, їхню кількість і час обробки. У синтетичному записі кадри з індексами 48–52 навмисно втратили текстуру.

## Відтворення дослідження

Підготовка публічних даних виконується окремо від запуску демо. Архіви та зображення зберігаються локально в `data/`. Версії джерел, правила вибірки та контрольні суми наведено в [описі датасетів](datasets/README.md). Обсяг вихідних файлів — близько 1,46 ГБ.

```sh
docker compose run --rm demo python scripts/fetch_data.py all
docker compose run --rm demo python scripts/prepare_data.py
docker compose restart demo
```

Після перезапуску у списку записів з’явиться UAV-VisLoc. Для нього карта і позиції беруться з публічних анотацій, прямокутник показує перевірений фрагмент ортофото. Для синтетичної сцени маршрут задано генератором.

За наявності підготовленого `data/manifest.csv` експеримент виконується однією командою:

```sh
docker compose run --rm demo python experiment.py --output results/reproduced
```

Оригінальні вимірювання зберігаються в [results](results). Основні файли:

| Файл | Вміст |
|---|---|
| `pairs.csv` | Зафіксовані кадри, позитивний і негативний еталони та поділ за послідовностями |
| `development.csv`, `frozen.json` | Вибір параметра CLAHE й контрольна сума вхідного переліку |
| `samples.csv`, `errors.csv` | Вимірювання для кожної пари та діагностичні приклади помилок за порогом |
| `summary.csv`, `quality.png` | AP, зміни AP, частка пар із менш ніж чотирма збігами, затримки та пропускна здатність |
| `environment.json` | CPU, ОС, версії бібліотек і кодека для інтерпретації швидкодії |

### Протокол

1. Для кожного кадру беремо позитивний і негативний еталони. Окремі польоти цілком належать до розробницької або тестової частини. VPAIR оцінюється незалежно. Вхідні зображення переводимо у відтінки сірого і вписуємо в 384 × 288 зі збереженням пропорцій.
2. Будуємо контрольований запис із послідовних кадрів (10 кадрів/с). Для кожної послідовності готуємо п’ять версій: чисту, H.264 з CRF 28 і 43, розмиття Гауса з σ 1 і 3 пікселі. Чисту й розмиті версії зберігаємо без втрат. Еталони спільні для всіх умов. В UAV-VisLoc фотографії зазвичай знято з інтервалом 2–4 с, а найбільший інтервал у тестовому фрагменті становить 39 с. Кодування зі швидкістю 10 кадрів/с моделює вплив компресії на задану послідовність. Для висновків про втрати пакетів чи нативний відеопотік потрібні окремі записи.
3. ORB та AKAZE виділяють локальні ознаки. Оцінка пари — кількість взаємних пар дескрипторів, що пройшли тест відношення відстаней 0,8 в обох напрямках. Порожня відповідь отримує оцінку 0. Поріг у чотири збіги використовується лише для діагностики. AP враховує весь порядок оцінок і об’єднує однакові значення на одному порозі.
4. CLAHE застосовується лише до кадру. Розмір сітки — 8 × 8. Межу обрізання гістограми обираємо з 1, 2 та 4 за найвищим середнім AP на розробницьких польотах, з однаковою вагою для двох методів і п’яти умов. За рівності беремо менше значення. Далі порівнюємо зафіксований варіант із вимкненим CLAHE на тесті.
5. Показуємо p50 і p95 часу алгоритму на одну пару з повторним обчисленням ознак еталона. Кадр декодується один раз для двох порівнянь. Його час декодування записано окремо. Виміряні **пари/с** включають читання кадрів, завантаження обох еталонів і обчислення. За двох пар на кадр швидкість обробки запису в кадрах/с дорівнює половині цього значення. Відтворення демо має власний темп.

### Перевірка

```sh
docker compose run --rm demo python -m unittest discover -s tests -v
```

## Результат

На розробницьких польотах 05 і 06 обрано CLAHE з межею 2,0. На кожному з двох незалежно оцінених тестових фрагментів було 24 кадри й 48 розмічених пар. У таблиці наведено AP для ORB до та після застосування CLAHE.

| Умова | UAV-VisLoc, політ 10 | VPAIR, зразок |
|---|---:|---:|
| Чистий кадр | 0,442 → 0,482 | 0,727 → 0,658 |
| H.264, CRF 28 | 0,474 → 0,514 | 0,558 → 0,614 |
| H.264, CRF 43 | 0,557 → 0,502 | 0,538 → 0,523 |
| Розмиття, σ 1 | 0,470 → 0,489 | 0,658 → 0,678 |
| Розмиття, σ 3 | 0,569 → 0,495 | 0,635 → 0,642 |

Для ORB на обох тестових фрагментах CLAHE допоміг за CRF 28 і слабкого розмиття, а за CRF 43 знизив AP. Для AKAZE за CRF 28 AP зменшився на обох наборах. На чистих парах UAV-VisLoc без CLAHE медіана затримки становила 12,4 мс для ORB і 43,7 мс для AKAZE. Виміряна швидкість з читанням обох еталонів — 25,0 та 9,8 кадру/с відповідно (Intel Core i9-9880H, Docker, один потік OpenCV).

Багато пар дали дуже мало збігів. Зокрема, на чистому тесті UAV-VisLoc без CLAHE жодна пара AKAZE не подолала діагностичний поріг у чотири збіги. AP усе ще враховує порядок оцінок 0–3. Знаки змін стосуються цих коротких фрагментів. Для узагальнення потрібні інші незалежні польоти. Точність позиції в метрах у цьому досліді не вимірювалася.
